D1: Specification Document

Current site: Single-page Vite + React 18 app. Page chrome is React; the interactive map is D3 over us-atlas TopoJSON. Deployed as a static site on GitHub Pages under the /measles-dashboard/ base path.

GitHub: https://github.com/ACCIDDA/measles-dashboard

Requirements

Functional Requirements

Definite/Completed

  • Data displays accurately based on county and school
  • Decouple hard-coded NC and CA data from the existing project repository
  • CHECK: Generalize to measles-dashboard-StateCode API that other states can follow
  • Accept data from measles-XX state repositories, given that no 404 error is received
    • 404 error recieved → state will remain inactive
    • No error → populate map with state’s data
404 Fallback

Our initially outlined 404 plan is completed and functional.

  • Accept data from measles-XX state repositories
    • 404 error recieved → catch error → state marked inactive → rendered on map as grey
    • No error → state marked active → assign state tier and color → populate map with state’s data
  • When a inactive state is clicked, use the existing toast "Data not yet available for [state]"
  • If inactive state accessed from URL, D3 map package handles the display
    • Centers on grey selected state, back button shown
    • Next click routes back to US overview
Interfaces

Interfaces remain consistent with original design and functionality, as agreed upon by client & team.

Improbable/Uncompleted

  • CHECK: Data cleaning scripts to take data and match it to required API for use in dashboard
  • CHECK:Scripts to validate each individual API
  • Moving to Vercel
    • Budget constraints from ACCIDDA team & a need for collaboration prevented us from exploring alternative hosting options

Non-functional

Definite/Completed

  • Usability: The API should be able to be used by health officials from varying states. The user instructions are understandable to scientists without a software engineering background.
  • Reliability: Should be accessible at all hours of the day/even after new information is updated
  • Performance: Should be able to handle concurrent users from all 50 states without loss
  • CHECK: Supportability: APIs should come with regressions tests and appropriate documentations
  • Physical: Should work on web devices
  • Design: same consistency in naming and typography as currently website holds
  • CHECK: Implementation: Application must expose APIs written in a language that is accessible to the users (ideally python)
    • Will continue to host on GitHub Pages (as opposed to Vercel or other platforms) because of client's hosting preferences
    • Must remain static to keep free access
  • Interface: Leverage the imuGap model for Bayesian model as necessary for estimation.

Perhaps

  • CHECK:Supportability: Support light and dark mode

Improbable

  • Collecting data from all states and imputed into the ACCIDDA dashboard
    • Client did not request data collection for project
